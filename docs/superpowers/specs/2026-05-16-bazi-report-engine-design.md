# 八字知识与报告引擎 MVP 设计

**日期**: 2026-05-16

## 背景

本项目以命理推算为主题，但第一阶段不做完整算命应用，也不先做视觉界面。我们先建设一个稳定的知识与报告引擎：输入出生资料和关注主题，得到透明、可检查、边界清晰的八字结构化报告。

参考方向来自 `ming-li` 仓库、传统八字知识体系、二十四节气历法资料，以及命理/占星咨询伦理规范。参考内容只作为产品与方法论启发，本项目会形成自己的文档、规则和实现。

## 目标

第一阶段交付“八字知识与报告引擎 + Markdown 结构化报告”。它应当能支撑后续 Web 可视化、样例库验证、紫微斗数和六爻扩展，但本阶段只聚焦八字。

## 已比较方案

### 方案 A: 纯知识引擎

只定义命理知识 schema、推演步骤、报告结构和伦理规则。优点是最快建立地基，缺点是短期没有可读成品，难以验证报告体验。

### 方案 B: 知识引擎 + 报告生成器

在知识结构基础上输出 Markdown 报告。优点是能同时验证推演数据、语言风格、伦理边界和报告结构。缺点是需要更早定义报告 schema。

### 方案 C: 知识引擎 + 报告生成器 + 样例库

在方案 B 的基础上加入 3 到 5 个脱敏样例，用于测试报告稳定性和红线审查。优点是质量更扎实，缺点是第一步稍重。

## 决策

采用方案 B 作为 MVP，并在数据模型和验收标准中预留方案 C。第一版必须能生成结构化 Markdown 报告；样例库可以作为后续增强，不阻塞 MVP。

## 用户输入

MVP 输入应覆盖：

- 日期类型：公历或农历。
- 出生日期：年、月、日。
- 出生时间：具体时间或传统时辰。
- 出生地：用于时区和真太阳时相关说明。
- 性别：用于大运顺逆等规则。
- 关注主题：整体、事业、财务、关系模式、阶段趋势等非越界主题。

如果必要信息缺失，引擎必须返回需要补充的信息清单，不得猜测。

## 中间结果

引擎需要形成可审查的中间对象：

- 四柱：年柱、月柱、日柱、时柱。
- 五行：各元素分布与强弱摘要。
- 十神：相对日主的十神关系摘要。
- 藏干：地支藏干展开。
- 旺衰：日主强弱的候选判断与依据。
- 格局候选：可能格局与不确定性说明。
- 用神喜忌：候选结论与置信说明。
- 大运流年：阶段性摘要，不做绝对预测。

MVP 可以先允许排盘结果由人工或外部工具提供，但必须在文档里明确来源。后续实现自动排盘时，排盘层必须和解读层分离。

## 报告输出

MVP 默认输出 Markdown 报告，包含：

1. 免责声明。
2. 命造卡片。
3. 四柱与五行摘要。
4. 结构分析：旺衰、格局、用神喜忌。
5. 性格倾向。
6. 优势与议题。
7. 当前阶段与大运流年概览。
8. 行动建议。
9. 术语简注。
10. 伦理边界提醒。

报告语言必须使用“倾向、结构、阶段、提醒、建议”等表达，不使用“必定、注定、一定会、死定”等绝对化语言。

## 伦理边界

系统必须拒绝或改写以下内容：

- 预测寿命、死亡时间、重大灾祸。
- 做婚配定论或评价两个人命中注定是否适合。
- 替代医疗、法律、心理、投资建议。
- 分析未授权第三方的完整命盘。
- 制造焦虑、诱导付费化解、售卖法事或物品。
- 否定用户提供的已发生事实。

当用户提出越界问题时，系统应解释边界，并引导到允许的替代问题。例如从“我们能不能结婚”转为“我自己的关系模式与当前阶段有什么值得觉察”。

## 质量门槛

MVP 完成时应满足：

- 所有正式报告都含免责声明。
- 所有判断都有输入或中间结果依据。
- 缺少关键信息时不生成完整报告。
- 报告不含红线内容。
- 报告中每个主要结论都给出可行动建议。
- 排盘规则和假设对用户可见。

## 后续扩展

后续阶段可以依次加入：

- 脱敏样例库与报告回归测试。
- HTML 可视化报告。
- Web 页面输入与预览。
- 紫微斗数领域报告。
- 六爻单事咨询。
- 报告导出为 PNG 或 PDF。

## 不做范围

MVP 不做：

- Web UI。
- 账户系统。
- 付费系统。
- 自动生成 PNG/PDF。
- 完整紫微斗数。
- 六爻起卦。
- 婚配定论、寿命灾祸预测、医疗法律心理替代建议。

## 自检

- 无未完成标记或未解释占位符。
- 设计聚焦单一 MVP，没有把 Web、紫微和六爻混入第一阶段。
- 关键实体、报告结构和伦理边界一致。
- 所有范围边界都可转化为 Spec Kit 验收条件。
