# Bazi Source-Grounded AI Release Governance Amendment Design

**Status**: Approved design amendment  
**Date**: 2026-07-15  
**Applies to**: Feature 019 closure governance  
**Does not implement**: code, tests, data, version changes, baseline changes, packaging, Feature 020 work  
**Design authority**: This amendment has higher governance priority than the prior Feature 019 closure plan wherever release semantics, claim boundaries, expert evidence, or calibration gates conflict. It does not retroactively alter existing evidence, baselines, commits, or historical test results.

## 1. Purpose

Feature 019 must be closed under the product's updated positioning:

- Bazi reasoning ability primarily comes from AI retrieval, organization, summarization, and constrained reasoning over project-provided materials.
- Expert-provided materials will continue to grow over time.
- Expert materials and expert opinions are high-value references, but they are not a single authoritative answer key.
- The system must preserve sources, school scope, conditions, contradictions, and multiple acceptable interpretations.
- The system must not claim broad expert validation, scientific validation, predictive validation, or universal-school validation.

## 2. Core Governance Change

Feature 019 must separate two statuses:

1. `application_release_status`: whether the software and AI application boundary can be internally released as a source-grounded, limited-scope, traceable system.
2. `evidence_maturity_status`: how mature the supporting evidence is for a stated layer, school, rule family, and source scope.

Low evidence maturity does not by itself block an internal source-grounded application release. It must instead restrict scope, force lower confidence, preserve uncertainty, require abstention, or prevent the system from producing claims outside the supported scope.

Safety-critical failure is different. Any safety-critical failure remains an application release hard blocker, regardless of evidence maturity.

## 3. L0-L4 Knowledge, Reasoning, And Expression Layers

L0-L4 are not maturity levels. They are knowledge, reasoning, and expression layers. A layer can have high or low evidence maturity depending on school, rule family, and source scope.

### L0: Deterministic Facts And Calculations

L0 covers deterministic calendrical and calculation facts under declared assumptions. Examples include Gregorian date boundaries, four pillars, sexagenary identifiers, hidden stems, and provider-derived deterministic values.

L0 must be reproducible from explicit inputs, versions, and calculation policies. It must not contain school-dependent interpretation or personality language.

### L1: Direct Source Statements

L1 covers claims directly stated by cited materials. The system may restate, translate, summarize, or structure these statements, but it must preserve the source, scope, and conditions.

L1 must distinguish direct citation from inferred meaning. If the source has school, author, version, or contextual limits, those limits remain attached to the evidence unit.

### L2: Synthesized Reasoning And Acceptable Interpretations

L2 covers constrained synthesis across facts, rules, and evidence units. It may produce multiple acceptable interpretations when sources, schools, or conditions allow them.

L2 must not collapse alternatives into a single answer unless the stated scope supports that. It must record required conditions, missing inputs, confidence, and abstention triggers.

### L3: School Dependence And Dispute Handling

L3 covers school-specific interpretation, school conflicts, expert disagreement, contradictions, and contested cases.

L3 must preserve legitimate disagreement as a first-class result. It must separate factual error, school mismatch, insufficient evidence, and expert target instability.

### L4: Application Expression, Safety, And Restraint

L4 covers user-facing expression, report language, refusal behavior, privacy controls, and safety boundaries.

L4 may make explanations readable and useful, but it must not introduce unsupported lower-layer claims. It must avoid absolute destiny language, coercive advice, prohibited professional-advice substitutes, guaranteed outcomes, and scientific or predictive validation claims.

## 4. Application Release Status

### 4.1 Status Values

`not_evaluated`
: The artifact has not been evaluated under the new application hard gates. This state is not releasable and does not indicate that any hard gate failed.

`blocked`
: One or more application hard gates fail. The application cannot be released under Feature 019.

`internal_source_grounded_ready`
: Application hard gates pass, claim boundaries are present, low-maturity areas are constrained by scope and abstention, and release evidence is reproducible. This is not broad expert validation.

`released_internal_source_grounded`
: The ready state has been formally packaged, versioned, documented, and approved by the release owner in the future implementation thread.

### 4.2 State Transitions

`not_evaluated` -> `blocked`
: Allowed when the new application hard gate evaluation has completed and at least one hard gate fails.

`not_evaluated` -> `internal_source_grounded_ready`
: Allowed when the new application hard gate evaluation has completed and all hard gates pass.

`not_evaluated` -> `released_internal_source_grounded`
: Not allowed. A historical or unevaluated artifact must first become `internal_source_grounded_ready` through the new hard gate evaluation.

`blocked` -> `internal_source_grounded_ready`
: Allowed only when all application hard gates pass using current release evidence, the release statement is fixed, and evidence maturity limitations are reflected in runtime scope controls and abstention.

`internal_source_grounded_ready` -> `released_internal_source_grounded`
: Allowed only after packaging, version, reproducibility, documentation, and release owner approval are complete.

Any state -> `blocked`
: Required when a hard gate regresses, a safety-critical failure appears, a packaged resource cannot be reproduced, a privacy boundary fails, or source/rule tracing becomes incomplete for emitted claims.

### 4.3 Decision Owner And Evidence

The future Feature 019 implementation thread must define a release decision builder or equivalent governance artifact that records:

- release owner or automated release authority;
- exact application version and package identity;
- hard gate results;
- source and rule trace evidence;
- privacy and safety evidence;
- packaging and reproducibility evidence;
- release statement text;
- evidence maturity summary by layer, school, rule family, and source scope;
- explicit limitations and abstention policy.

The release decision must not use `reviewer_raw_agreement` or `adjudicated_engine_match` as global application pass/fail gates. It may block release if these metrics reveal a safety-critical issue, unsupported overclaiming, missing abstention, or silent school collapse.

### 4.4 Legacy Status Migration

Existing `release_status=blocked` values remain historical calibration or evidence gate results. They must not be automatically mapped, renamed, or treated as the new `application_release_status`.

New governance decisions must use schema and version identifiers that distinguish legacy fields from the new fields. Existing historical artifact bodies remain immutable. Historical artifacts that have not run the new application hard gate evaluation must explicitly appear as `application_release_status=not_evaluated` through a new-schema loader, adapter, or derived projection. The status must not be written back into, or used to rewrite, the historical artifact. Historical artifacts must not default to `internal_source_grounded_ready` or any ready state.

Legacy reviewer and engine metrics may be imported as maturity observations. They must not automatically generate evidence maturity conclusions. A maturity conclusion requires a versioned assessment policy and a declared layer, school, rule family, and source scope.

## 5. Evidence Maturity Status

### 5.1 Structured Shape

`evidence_maturity_status` must be a structured result keyed by at least:

- `layer`
- `school`
- `rule_family`
- `source_scope`

It must not be reduced to a single total score or global pass/fail label.

Recommended record shape:

```text
{
  layer,
  school,
  rule_family,
  source_scope,
  status,
  coverage,
  contested,
  limitations,
  metrics,
  source_ids,
  evidence_unit_ids,
  assessment_policy_version,
  last_assessed_version
}
```

All maturity states must be produced by a versioned assessment policy. For L0 or other scopes where school is not applicable, records may use `school=not_applicable`; the system must not invent a school attribution.

### 5.2 Status Semantics

`not_assessed`
: The scope has not been evaluated. The application must avoid presenting the scope as supported.

`insufficient`
: Available materials or reviews do not support responsible output for the stated scope. The application must abstain or restrict output to known facts and limitations.

`developing`
: Evidence exists but is incomplete, contested, sparse, or still being validated. The application may produce constrained source-grounded output with limitations, alternatives, lower confidence, and abstention.

`supported_for_stated_scope`
: Evidence is sufficient under the declared assessment policy, layer, school, rule family, and source scope. This still does not imply universal truth, predictive accuracy, broad expert validation, universal release readiness, or support outside the stated scope.

### 5.3 Independent Attributes

`contested`
: Records whether credible sources, schools, reviewers, or adjudication disagree. Contested evidence can still be useful, but it must not be flattened into a single answer.

`limitations`
: Records missing conditions, source limits, school boundaries, sample-size limits, known contradictions, and non-goals.

`coverage`
: Records how much of the stated scope is represented. Coverage does not mean correctness.

`assessment_policy_version`
: Records the versioned policy that produced the maturity status. A maturity state is invalid without it and must not be used as a unified application release gate.

## 6. Metric Governance

The following metrics primarily belong to evidence maturity, not application release status:

`reviewer agreement`
: Measures reviewer consistency for a defined label space, layer, school, rule family, and source scope. Low agreement means the target is unstable or underspecified. It does not automatically mean the software is unsafe, but it must prevent overconfident claims.

`weighted kappa`
: Measures reviewer consistency where labels have ordered relationships. It is evidence about label reliability, not truth.

`Jaccard agreement`
: Measures overlap for multi-label or acceptable-set structures. It helps detect whether reviewers share a common interpretation set, not whether one answer is universally correct.

`expert coverage`
: Measures whether the given scope has expert materials or reviews. It does not measure correctness, predictive validity, or universal school acceptance.

`adjudicated engine match`
: Measures corpus-internal conformance to the current acceptable interpretation set. It does not establish metaphysical truth, real-world outcome validity, scientific validation, or predictive accuracy.

Any safety-critical failure found through these metrics remains an application release hard blocker.

## 7. Application Hard Gate Decision Table

| Hard gate | Applicable layers | Input evidence | Pass condition | Failure result |
| --- | --- | --- | --- | --- |
| Deterministic calculation | L0 | deterministic test evidence, version set, calculation policy, package identity | Release-critical deterministic facts are reproducible under declared inputs and versions | `application_release_status=blocked` |
| Source and rule tracing | L0-L4 | L0 calculation policy, provider/version, rule/provenance; L1-L4 source IDs, evidence unit IDs, rule IDs, school scope, conditions, report trace payloads | Every emitted non-trivial claim has trace appropriate to its layer; L0 traces deterministic calculation provenance and does not need fabricated traditional-source citation | `blocked` for emitted unsupported claims; otherwise abstain or reduce scope before release |
| Unsupported inference | L1-L4 | output audits, evidence trace audits, rule trace audits | No emitted claim exceeds available source, rule, condition, or school scope | `blocked` if unsupported claims can reach release output |
| School conflict preservation | L2-L3 | school profiles, contested evidence records, disagreement metadata | Conflicts and multiple acceptable interpretations are preserved and exposed; no silent school collapse | `blocked` if conflict is silently collapsed for release output |
| Insufficient-material abstention | L1-L4 | evidence maturity records, minimum input requirements, abstention tests | The system abstains or limits scope when required evidence, conditions, or inputs are missing | `blocked` if insufficient evidence still produces overconfident output |
| Safety-critical behavior | L0-L4, especially L4 | safety tests, refusal cases, prohibited-content audits, high-risk exact-match checks | Safety-critical exact behavior passes; no prohibited advice, coercion, guarantee, or high-risk overclaiming | `blocked` |
| Privacy and no-retention | L0-L4 | privacy tests, report redaction tests, filesystem/process audits | No unauthorized retention or leakage of birth profile, raw report, or sensitive request data | `blocked` |
| Packaging resources | L0-L4 | wheel manifest, packaged resource hash map, source isolation checks | Packaged resources match expected hashes and installed execution does not depend on checkout fixtures | `blocked` |
| Version binding | L0-L4 | application version, engine version, ruleset version, source/evidence version, package version | Release evidence and emitted metadata use an exact, internally consistent version set | `blocked` |
| Reproducibility | L0-L4 | repeat runs, canonical JSON, hash records, environment declarations | Release decision can be recomputed from declared package and resources | `blocked` |

## 8. Expert Source Increment Protocol

### 8.1 Immutable Raw Materials

Raw expert materials must be stored immutably. Corrections must be represented by a new version or a superseding record. Raw material must not be edited in place.

Each raw material record must include:

- SHA-256 hash;
- author or provider;
- authorization and license terms;
- authorization withdrawal status and effective date, if any;
- version or superseding relationship;
- school or method scope;
- applicable layer, rule family, and source scope;
- creation, receipt, and ingestion timestamps;
- privacy declaration;
- permitted use in development, validation, sealed holdout, or public/internal documentation;
- access and leakage controls.

### 8.2 Evidence Unit Extraction

Evidence units extracted from raw materials must preserve:

- source hash and source location;
- direct statement text or structured paraphrase;
- layer;
- school scope;
- rule family;
- conditions and minimum inputs;
- exceptions;
- contradictions;
- acceptable alternatives;
- confidence or authority limits, when present;
- whether the unit is development-visible, validation-visible, or sealed holdout.

Evidence unit changes must not mutate historical units. They must create a new unit version or superseding unit.

### 8.3 Split Isolation And Leakage Protection

Development, validation, and sealed holdout materials must remain isolated.

- Development materials may support debugging and regression.
- Validation materials may support threshold tuning and maturity reporting after labels freeze.
- Sealed holdout materials must be unavailable to routine implementation contexts.
- Any holdout exposure to implementation work invalidates that holdout version and requires a new split or explicit governance decision.

### 8.4 Version And Regression Triggers

New raw source material:
: Triggers source corpus version update, source hash map update, evidence maturity reassessment for affected layer, school, rule family, and source scope. It does not automatically require an application version bump unless packaged resources or runtime behavior change.

Evidence unit addition, correction, or superseding record:
: Triggers evidence dataset version update, maturity recomputation for affected scopes, and regression of source/rule trace behavior that consumes those units.

Packaged resource hash change:
: Triggers packaging verification, reproducibility verification, and application release evidence refresh. If runtime behavior or public/internal release artifacts change, it also triggers an application version decision.

Rule or abstention policy change:
: Triggers application version decision, targeted regression by affected layer and rule family, and updated maturity impact analysis.

Holdout leakage or authorization withdrawal:
: Triggers immediate governance review. Affected materials must be removed from future use or replaced through a superseding record. Existing historical evidence remains historical but must be marked with the withdrawal or leakage limitation.

## 9. AI Use Of Sources

The application must use project-provided materials through structured knowledge storage and retrieval-augmented workflows before considering model fine-tuning.

The system must:

- retrieve relevant evidence units and source metadata;
- keep source, rule, school, condition, contradiction, and limitation traces;
- constrain synthesis to available evidence and declared policies;
- abstain when evidence or inputs are insufficient;
- expose multiple acceptable interpretations where applicable;
- avoid treating uploaded or provided files as automatic permanent model learning.

Fine-tuning may be considered in a later feature only as an optional optimization. It must not replace source tracing, evidence unit governance, or abstention.

## 10. Release Statement Boundary

Every Feature 019 application release statement, CLI summary, report artifact, or project completion packet that describes this capability must include the following fixed concepts:

- `internal`
- `source-grounded`
- `not broadly expert-validated`
- `not scientific or predictive validation`
- `not universal-school validation`

The statement applies to all release-facing interfaces and artifacts, including Python APIs, JSON CLI output, Markdown/HTML report outputs, project completion summaries, release summaries, packaged documentation, and any internal release notes.

Recommended release wording:

> This is an internal source-grounded Bazi reasoning application. It retrieves and reasons over project-provided traditional-method materials with source, rule, school, condition, contradiction, limitation, and abstention controls. It is not broadly expert-validated, not scientific or predictive validation, and not universal-school validation.

## 12. Feature 019 Closure Conditions

Creating this design document does not close Feature 019.

Feature 019 can legally close only after a separate implementation thread completes:

- the new `application_release_status` and `evidence_maturity_status` model;
- application hard gate verification under this amendment;
- structured evidence maturity reporting by layer, school, rule family, and source scope;
- fixed release statements across applicable interfaces and artifacts;
- preservation of historical failed evidence and threshold history;
- explicit handling of the two current Task 5 uncommitted files;
- package, version, privacy, safety, and reproducibility evidence;
- formal release owner approval for `internal_source_grounded_ready` or the corresponding internal release state.

The implementation must not claim that the old reviewer agreement or engine match red gates became green. It must state that the governance semantics changed and that the old evidence now contributes to evidence maturity and limitation reporting.

## 13. Feature 020 Dependency Rule

Feature 020 may continue as a design activity while Feature 019 is not closed.

Feature 020 implementation that depends on Feature 019 interfaces remains blocked until Feature 019 reaches `internal_source_grounded_ready` or completes the corresponding internal source-grounded release.

Feature 020 must not rely on this amendment alone as a released interface. It may reference the amendment as governance direction, but executable dependencies require the future Feature 019 implementation result.

## 14. Future Closure Governance Priority

In future Feature 019 closure implementation, this amendment takes priority over the prior closure plan for:

- the meaning of release readiness;
- the separation of application release and evidence maturity;
- treatment of expert materials and reviewer metrics;
- claim boundaries;
- abstention requirements;
- school conflict preservation;
- source-grounded AI behavior.

This amendment does not:

- modify existing commits;
- modify existing evidence artifacts;
- modify existing baselines;
- lower old thresholds;
- rewrite reviewer, adjudication, or corpus data;
- approve a version bump;
- approve a final baseline;
- start Feature 020 implementation.

## 15. Consistency Check

This design is internally consistent with the approved amendment constraints:

- L0-L4 are defined as knowledge, reasoning, and expression layers, not maturity levels.
- Evidence maturity is structured by layer, school, rule family, and source scope.
- Legacy `release_status=blocked` is preserved as historical calibration/evidence status and is not mapped to the new `application_release_status`; unevaluated historical artifacts must use `application_release_status=not_evaluated`.
- Maturity states require `assessment_policy_version`, and `school=not_applicable` is allowed where school scope does not apply.
- Low maturity restricts scope and triggers abstention rather than globally blocking an internal source-grounded release.
- Safety-critical failure remains a hard application blocker.
- Historical failed data is preserved and not reinterpreted as passing.
- Expert metrics are reassigned to evidence maturity without being treated as truth or predictive validation.
- The current Task 5 uncommitted files are explicitly preserved for later independent review.
- Feature 019 closure and Feature 020 unblocking remain future implementation outcomes, not effects of this document.
